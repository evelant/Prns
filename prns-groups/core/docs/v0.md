# Group communication: initial behavioral contract

This is the intended behavioral contract, including unimplemented policy and
recovery paths. The [portable group core](../README.md) and component READMEs
identify current APIs; this document alone does not establish an implemented
guarantee or interoperable wire format. The [architecture](design.md),
[policy alternatives](policies.md) and security analysis (separate integration)
explain the tradeoffs. The [embedded guide](embedded.md) owns target support and
release gates.

## 1. Scope and decisions

Build a reusable library above Reticulum for authenticated, bounded record
distribution to independently credentialed endpoints. Applications own schemas,
projections, history permissions and effects. Target native hosts and `no_std`
embedded devices through a fixed-storage core requiring neither `std` nor `alloc`
and platform adapters, using existing
`SINGLE`, Link, request and Resource operations. Python routers require no core
changes; a Python application still needs this application protocol. The initial
host experiments are historical reference work, not shipping dependencies.
Core primitives and the transaction coordinator are present here. MLS, record
services and native enrollment/transport are following integrations. Complete
embedded participation, wire interoperability and the wider policies remain open.

| Decision for the first version | Reason and accepted limit |
| --- | --- |
| One fixed owner approves and orders control changes; application data has multiple writers. | Avoid distributed agreement initially. Owner loss blocks membership changes and owner-committed group key updates, including MLS Commits. No automatic failover or owner replacement. |
| Cached membership for publication. | Permits disconnected work. Unknown removals can expose stale sends; strict ordered admission is a later profile. |
| Public authenticated records provide the portable baseline; private profiles are qualified separately. Best-effort durable storage is the initial storage policy. | Proves replication independently of confidentiality. Applications requiring secrecy must use a qualified private profile; no silent profile change. |
| MLS is the preferred private protocol, with one client per endpoint incarnation. `mls-rs` is the implementation under qualification. | Start with ESP32-S3/PSRAM; smaller boards may be excluded from membership. Follow the [embedded support gates](embedded.md); isolated library builds and host allocations do not qualify firmware membership. |
| One named remote best-effort custodian is the default request; direct delivery can proceed while custody is pending. | Small operational footprint. Custody is a separate fact; FIFO eviction can defeat delivery. Reserved custody and replica quorums are deferred. |
| Fixed publication targets and deadline; default and initial maximum delivery window 14 days, configurable downward. | Bounds outstanding work. Expiry does not revoke a device, and retries do not restart the window. Longer retention needs a later supported profile or application-owned archive. |
| Small inline records first; application references may name external objects. | Avoid inventing attachment encryption and chunk recovery simultaneously. A record receipt never covers those external bytes. |
| Optional history via explicitly authorized transfer. | No implicit history access on enrollment; new transfers have separate obligations and provenance. |

Every profile requires authenticated producers and control. For the initial
homogeneous private membership policy,
ordinary members can read and publish; namespace subscriptions filter delivery,
not decryption. Distinct reader audiences need separately specified protection;
for MLS, a different reader audience requires a different security group.
The public profile authenticates its writers while allowing non-member readers.
An owner-authorized ingress member may accept outside producers without making
them readers. More elaborate writer roles remain a policy extension.

Non-goals for this version: threshold governance, automatic authority recovery,
strict revocation freshness, arbitrary policy combinations, guaranteed archives,
generic merge/CRDT logic, command execution, live media, resumable attachments,
qualification of every mobile/embedded board and group size, and a new Reticulum
core protocol. A representative embedded build and resource gate is required
before selecting the production foundation.

## 2. Identities and durable objects

The invitation pins a **group ID** derived from a domain-separated hash of a
canonical genesis descriptor, including fresh randomness, initial owner key and
profile. It also carries bootstrap contacts. The ID is an application address,
not a cloned Reticulum destination or a secret granting membership. Each endpoint
has its own transport identity and credentials. The owner binds each endpoint's
incarnation and application signing key to its MLS credential when applicable.

| Object | Required semantic bindings |
| --- | --- |
| Control transition | Group, predecessor hash, owner signature, policy version, complete change, authorization-era/barrier semantics, and the profile-specific protected transition when required. For MLS, bind its Commit/epoch and any routine closure's preceding-epoch time/cutoff. |
| Logical record | Group, namespace/schema, original author and incarnation, random publication nonce, original authorization reference, authenticated immutable original reader-audience reference, payload, bounded causal references, initial admission time and immutable deadline. The original producer signs their digest with a protocol-specific signing context. |
| Publication envelope | Record digest, issuing endpoint, authorization era/control reference, security profile and authenticated protection-context reference, intended recipient/incarnation/key binding when required by the profile, explicit delivery target-set reference, obligation reference and protected representation. An MLS epoch is one kind of context. A repaired envelope has a new ID. |
| Delivery obligation | Record digest, issuer, target endpoint incarnations, subscription revisions, receipt meaning and deadline. Its identity remains separate from the envelope. |
| Evidence | Issuer and role, record/obligation or retained-envelope identity, exact meaning, endpoint incarnation and applicable control reference. Signatures survive forwarding. |

Use full collision-resistant digests internally; widths, canonical encoding and
signature domain labels must be fixed together in the wire specification. The
application's operation key binds a nonce and fixed deadline and maps durably to
a record ID: reuse with different content is `IdempotencyConflict`, not another
publication. Reject expired operation keys even after that mapping is collected;
a fresh deadline requires an explicitly new operation key. Re-encryption does not
change the record or create new targets. Reject conflicting authenticated bytes
under any claimed identity.
The original cryptographic reader audience is distinct from subscription and
delivery targets; authenticate both references and retain the evidence needed to
resolve them during repair. Delivery filtering does not revoke decryption rights.

Private inner fields, receipts and membership records are encrypted. A blind
custodian indexes opaque ciphertext by scoped handles; it need not learn record
digests, rosters or application namespaces. For the MLS candidate, raw headers reveal
group ID, epoch, content type and AAD to that store. Keep AAD empty or deliberately
public and all sensitive record/control fields inside encryption. The MLS
candidate accepts this group correlation; opaque handles do not conceal it.
Other profiles must specify their own visibility, including recipient identifiers,
key-wrapper lists and correlation between shared object copies.
The custodian's store/fetch/delete capabilities and quotas are separate from
group membership. In v0 members schedule fan-out;
the custodian is an opaque store, not an interpreter of hidden group obligations.
Traffic patterns and service contacts remain observable.
Producer signatures and transferable receipts provide provenance, not deniability.

## 3. Authority, enrollment and failure

Control state is `ready(head)`, `repairing`, `conflicted` or `rejoin-required`.
Only the fixed owner signs successors. A higher counter is not sufficient:
verify ancestry, the existing policy and the complete proposed change.

For MLS, the owner is the only permitted committer. It prepares a transition,
validates the resulting roster, and durably commits the control decision, MLS
state and exact outgoing Commit/Welcome work before publication. Receivers inspect
the staged Commit and merge only with matching valid governance evidence. Missing
halves wait; neither a standalone roster edit nor an unapproved MLS Commit changes
effective membership. Rekeying may advance the epoch without changing the roster.

Every profile tracks an authorization era separately from its crypto context:
only verified routine encryption-key updates preserve it. Membership,
role/grant, incarnation, credential/signing-key
or policy changes and declared compromise recovery create a new barrier/era,
including removal and re-addition with the same apparent roster. Unknown changes
receive no routine exception. Bind era progression to this same control chain;
it is not independently editable membership state. A barrier invalidates
prior-era live admission in every profile; key replacement/purge depends on the
profile. It does not universally delete recipient keys also used by other groups.
For the MLS candidate, every barrier starts a fresh epoch, including
role/policy-only changes, so one epoch never straddles eras. Use a path-bearing
fresh-key Commit; recovering a compromised
member still requires its fresh contribution or removal and applicable credential
remediation, not only the owner's self-update.
[OpenMLS staged processing](https://book.openmls.tech/user_manual/processing.html).

Private profiles require encrypted governance and authenticated bootstrap.
The MLS candidate additionally requires encrypted member handshakes,
authorized KeyPackage distribution, and an encrypted Welcome tree or protected
owner-to-joiner bootstrap. No public GroupInfo/tree or external-join path in v0.
Welcome's outer references and storage access can still reveal joining activity.
The owner is an MLS reader, not a content-blind authority.

For MLS, members may generate fresh leaf Update proposals for the owner to commit.
Owner self-updates alone do not necessarily heal another member's compromised state.
Queue a local refresh intent while the owner is unavailable; submit an actual MLS
Update when it can be incorporated. Valid pending proposals prevent further
application publication in that epoch until the owner's transition is processed.
Cached sending can otherwise continue while crypto state permits. The
proposed maintenance defaults (separate integration)
target daily active-member refresh, warn at seven days and trigger owner action
for still-stale ordinary members at fourteen days. These are separate from delivery
expiry and promise no bounded post-compromise recovery during owner outages.
A stolen signing credential needs separate verified replacement, not merely an
encryption-key update.
[MLS Commit rule](https://www.rfc-editor.org/rfc/rfc9420.html#section-12.4).

Enrollment requires an owner-authorized credential binding and a fresh endpoint
incarnation. In MLS, persist KeyPackage private material before advertising it
and prevent duplicate allocation/consumption. Ordinary restart retains committed state;
an ordinary member's reinstall, lost state or detected/declared backup restore
requires a fresh incarnation and rejoin. Do not clone live MLS state between
devices. The owner cannot use this shortcut: loss or unsafe rollback of its
required control or profile state requires a new group in v0.
After owner credential compromise, that migration needs fresh independently
verified authority credentials, not reuse of the compromised key.

The owner may be offline while existing members publish. Control changes and
owner-committed group key updates then wait. Recipient-key rotation needs its
own profile-specific rules; those are not specified here. No election, timeout-based promotion or competing
owner is permitted. Permanent owner loss creates a new group/address in v0.
Explicit authority transfer/recovery is a later protocol, not a counter increment.
Two valid incompatible successors cause `MembershipConflict`: preserve evidence,
stop new publication, admission and private disclosure and require explicit
migration to a new group; v0 does not resolve the fork under the same address.
Existing local records remain readable. A partition can conceal a fork until contact;
this detects equivocation, not Byzantine consensus.

## 4. Publication and stale membership

Local publication is `prepared → committed → distributing`. `publish` reports
local acceptance only after committing the record, idempotency mapping, fixed
targets/deadline, cryptographic changes and exact outgoing work. Missing remote
custody is reported as pending, not local publication failure. Backpressure before
commit returns a refusal; timeout after a possibly committed request means query
the same operation identity.

Resolve targets from the sender's authenticated membership and known subscription
revisions. Report that basis: “all” means all those explicit targets, not every
device that may exist elsewhere. New membership/subscription changes affect
future publications. Historical requests create separate obligations.

Receiver behavior is deliberately conservative across authorization/security
barriers. The MLS candidate adds a bounded exception for routine rekeys:

| Incoming state | Decision |
| --- | --- |
| Exact record already accepted locally | Return retained evidence and resume still-live obligations; do not apply it twice. |
| Unknown/later control state | Fetch bounded predecessors and verify them before new acceptance. |
| Matching locally accepted head and usable security context | Verify issuer, author rights, integrity, target and deadline; commit or refuse. This is local freshness only. |
| MLS ancestor epoch in the current authorization era, with no local acceptance | Accept only through verified routine transitions, retained receive state and a valid fixed epoch cutoff, plus all ordinary authorization/target/deadline checks. |
| Prior authorization era, or unusable profile context, with no local acceptance | Reject this envelope for live delivery; provide an authorized correction or repair outcome. For MLS this includes an expired epoch cutoff or unavailable receive state. A claimed old creation time does not cross a barrier. |
| Conflicting history, invalid evidence or removed author | Stop/deny as appropriate; no private roster disclosure to an unauthorized requester. |

A still-authorized original author can re-authorize the same record under the
receiver's current context, preserving targets and deadline. A removed author
cannot. Sender timestamps, remote `Stored` acknowledgments and another member's
receipt do not prove admission before a removal. Consequently, an honest delayed
write from a subsequently removed author can be lost to a receiver that had not
accepted it. This is an explicit availability cost of the initial rule.

For MLS, an owner-authenticated routine closing transition binds a fixed
late-acceptance cutoff for the preceding epoch. Trial grace is 48 hours; compare zero and 14 days
before qualifying profiles. Validate the closure timestamp's future skew as well
as this cutoff and the original record deadline using the clock rules below;
retries, fetch and restart never extend
either. Counts/bytes/generation caps can require earlier repair. Apply available
verified control before application admission and recheck the era atomically at
receipt commit. A hidden newer barrier remains the existing cached-freshness
limitation. See [options and cases](policies.md#delayed-delivery-across-routine-rekeys).

Previously accepted local history remains valid as history; retained local
evidence can authorize restoration of that exact record. A fresh history import
from a currently authorized source is separate provenance, never retroactive
proof of live delivery or permission to execute old commands.

## 5. Profile catch-up, history and outside writers

Retries, audience preservation and explicit history permissions apply to every
profile. Epoch retention and ratchet rules below describe the optional MLS branch;
other private profiles require their own qualified key-lifecycle and recovery rules.

Ordinary retries resend the exact persisted envelope. On repair, creating fresh
ciphertext consumes fresh sending state; never roll back a ratchet to reproduce
it. Deduplicate previously accepted envelope IDs before attempting to decrypt
them again. MLS messages can require missing control and bounded out-of-order
state; exceeding those bounds returns a repair/rejoin outcome.
Compute envelope identity from the actual bytes. Duplicate fast paths still
authorize the requester before revealing evidence and enforce deadlines before
forwarding. A differently encrypted copy undergoes crypto verification before
logical-record deduplication.

**Changing protection can change the audience.** Adding a recipient key wrapper
or re-encrypting an old record into the current group would disclose it to newly added readers even if
they are outside its delivery targets. Permit group-wide re-encryption only when
the current reader set is a subset of the original permitted reader set. Otherwise
use an authenticated, recipient-specific repair exchange over a direct Reticulum
Link. Live-delivery repair verifies both endpoint credentials, current entitlement,
original reader eligibility, original target and original deadline. Do not
terminate that plaintext exchange at a blind relay. Bind the repair/import
envelope to its operation kind, record, original provenance, recipient incarnation
and current authority context.

For v0 this repair is an online exchange with the original author, or a source
authorized for explicit history import. It is not a second asynchronous pairwise
ratchet protocol. Newly enrolled devices receive history only through the latter
operation with an owner-authorized grant naming the recipient, source and allowed
history scope. Apply it under the selected freshness rule. An import has its own
transfer identity, authorized target and bounded deadline; the source signs these
bindings. The old record's identity, signature and deadline remain provenance,
not restrictions that would forbid this separately authorized historical transfer.
Import receipts cover the import obligation, never reopen or satisfy the original
publication's obligations. A current member cannot automatically reclassify a
removed author's unaccepted operation as live work.

For MLS, retain bounded receive state for past application epochs only within
the current era and its fixed cutoffs; this replaces the earlier zero-past-epoch proposal.
Delete consumed keys and bound skipped generations. Never retain whole rollback
snapshots as a delayed-decryption mechanism. A barrier must purge prior-era
application secrets after merging its transition, atomically with admission
invalidation. Keep necessary current/control state and application-owned
recoverable content according to policy; if needed state/content is lost, return
`RecoveryRequired` or `HistoryUnavailable`.
The original author needs a recoverable content copy for re-encryption: OpenMLS
discards sending keys, so the author's own ciphertext is insufficient. Retaining
plaintext/history, including encrypted-at-rest copies with accessible keys,
limits the practical benefit of forward secrecy for that retained content.
[OpenMLS key deletion and delayed messages](https://book.openmls.tech/forward_secrecy.html).

The 14-day deadline is not a secrecy bound. Offline members, retained skipped/
epoch keys, storage journals and backups can preserve older decryption material.
Deletion must cover the declared storage threat model, and inactivity/key-age
policy remains separate from delivery expiry. Direct repair/history framing must
also account for public Resource proofs (separate integration):
use hidden unpredictable framing per sensitive plaintext segment. Reticulum's
internal Resource prefix alone does not supply this protection.

Thus a blind custodian holding ciphertext is **not necessarily a recoverable
history archive**, and one surviving copy does not promise delivery across epoch
or credential changes. Applications needing recovery without an online plaintext
source need a separately specified archive/key-retention profile.

The initial MLS outside-producer path submits authenticated records to an authorized ingress member
over a directly authenticated Link. The ingress sees plaintext, validates the
producer's current grant and republishes while retaining original provenance.
It may repair on the producer's behalf only while that grant remains valid.
If ingress is unreachable, the producer keeps its local submission pending.
Offline blind-relay ingress and other profiles need a separately qualified
encrypted submission design. MLS
external proposals do not themselves carry ordinary application publications.
[RFC 9420 §12.1.8](https://www.rfc-editor.org/rfc/rfc9420.html#section-12.1.8).

## 6. Commit boundaries and evidence

| Boundary | Commit coherently before reporting success |
| --- | --- |
| Local publication | Stable record/idempotency mapping, obligations, deadline, cryptographic state and exact ciphertext/outbox entry. |
| Custodian storage | Complete retained representation, authorized storage request, retention/eviction terms, retry index and acknowledgment work. |
| Recipient receipt | Validated inline record, dedup/acceptance facts, consumed cryptographic state, obligations and receipt outbox. |
| Authenticated MLS application data rejected by our policy | Consumed cryptographic state and bounded rejection/replay facts, without application acceptance or `Received`. An uncertain-time record may remain bounded pending work. |
| MLS authentication or processing error | Discard the attempted Group and staged writes, reload committed state, and separately bound/quarantine invalid input. An error does not prove the library left its ratchets unchanged. Never persist an unauthorized control merge. |
| Authorization/security barrier | Approved control and the profile's required crypto changes, era invalidation, and outgoing control work. For MLS, purge prior-era application secrets after merging its transition. Serialize against delayed-record acceptance. |
| Application processing | Application projection or effect ledger and its input identity; the application defines its separate result. |

The persistence adapter must make crypto changes and these records one recoverable
transaction or specify an equivalent journal/recovery protocol. Separate databases
that can disagree after a crash are insufficient. Staged bytes may be cleaned up
after recovery; acknowledgment-eligible metadata must never refer to uncommitted
bytes. Do not release ciphertext or receipt work before the definitive commit.
If an adapter cannot meet a requested failure model, refuse that profile.
After an aborted or uncertain transaction, reload/reconcile in-memory crypto/profile state
from committed storage before further crypto operations. A database rollback
alone does not undo a mutated in-memory ratchet.

Require a backend with tested recovery and power-loss ordering for protocol/crypto
state: native transactions or an equivalent board-owned flash commit protocol.
SQL and full-state snapshots are not requirements. On embedded builds, bound
staging memory and flash writes and test interruption during commit and compaction.
State the actual payload commitment in evidence. Arbitrary backup rollback is
different: a store cannot reliably detect that its own entire history was rolled
back without an external anchor. Do not promise protection against undetected
hostile rollback.

`Stored` names the exact retained envelope and best-effort terms; it proves neither
decryption nor continuing availability. `Received` means the endpoint durably
accepted the authenticated record and inline body, not referenced attachments,
application processing/execution or human reading. A receipt for one endpoint
incarnation cannot satisfy a replacement incarnation.

Keep receipt, expiry, removal and known availability as separate facts. A late
receipt may establish historical receipt after an obligation closed, without
proving receipt before its deadline or reopening forwarding. `all received`
requires valid evidence for every original target; removed/expired targets are
reported separately. Reconcile signed receipts privately, with no receipts of
receipts. Custodians can forward evidence; they cannot manufacture group decisions.

FIFO eviction can remove the last copy in this profile. Persist a bounded loss
fact and stop claiming current availability. Reserve metadata capacity at
admission; reject additional work before deleting the only live obligation,
dedup entry or required cryptographic state. Application-owned archives may retain
accepted plaintext longer, but that is not a v0 custody guarantee.

## 7. Bounded synchronization and time

Use `hello → authenticate → compare heads → fetch control → inventory/fetch →
receipt reconciliation`. Service announces carry compact protocol capabilities,
not private group names or membership changes. A generic bounded bootstrap
response is separate from group authorization; do not promise typed errors for
requests silently rejected by the underlying transport allow-list.

Inventory pages contain references and sizes, not payloads. Scope them to an
authorized namespace/subscription and bind cursors to a stable inventory generation;
an expired cursor returns `RestartInventory`. Missing notifications are repaired
by another scan. Do not infer receipt from “highest seen” counters or summaries.
Bound page bytes/items, dependency depth, simultaneous fetches, CPU work and retry
traffic. Schedule control/receipts alongside content so neither starves indefinitely.

For the timed-expiry profile, require a clock adapter supplying a trusted UTC
interval plus monotonic elapsed time while running. Initial local admission fixes
the signed creation time and deadline; retries, relays and repairs preserve them.
Require `0 < deadline - creation <= maximum_window` and
`creation <= receiver_clock.upper + allowed_future_skew`. New acceptance requires
`receiver_clock.upper < deadline`; expiry requires
`receiver_clock.lower >= deadline`. An overlapping/unknown interval returns
`TimeUncertain`; it is not evidence of delivery or expiry. Signed creation times
fix the retry boundary, not proof that the writer's clock or claimed history is true.

Advance a persistent expiry watermark before or atomically with collecting replay
metadata; never decrease it on recovery. Refuse normal operation after a detected
backward clock/restore violation until the clock/state is repaired. Keep exact dedup and
obligation metadata through the deadline; collect it only once time safely passes
that boundary. Old signed records then remain expired even after their IDs are
collected. A malicious authorized writer can create a new record; this mechanism
does not deduplicate semantic intent. Clock confidence is an explicit v0 assumption,
not something learned from an arbitrary peer's claimed time.
Admission-rate/count quotas bound how many live IDs fit within that window.
Once evidence is collected, `progress` returns `EvidencePruned`, not “never
received.” A progress handle retains its original record identity and deadline;
an expired retry cannot silently become a new publication.

Application state snapshots, authority checkpoints and cryptographic rejoin are
different. In v0, snapshots are ordinary authenticated records with application
defined coverage; no generic automatic compaction follows. An archive consumer
retains every accepted sample within its chosen window while a dashboard projects
the latest value. The dashboard's state does not cancel archive obligations.
Bound retained control history; beyond it use owner-authorized bootstrap/rejoin,
without silently discarding local unsent application work.

## 8. Application and adapter contract

Conceptual operations, not finalized Rust signatures:

| Operation | Contract |
| --- | --- |
| `open_group(invitation, credentials, adapters, limits)` | Verify profile/authority; borrow network and persistence. Do not create or own another Reticulum node. |
| `publish(namespace, schema, operation_key, body, targets)` | The operation key carries its fixed deadline. Commit one immutable operation; return a queryable handle and actual acceptance level. |
| `subscribe(selector, revision)` | Persist an authenticated future-publication preference. History is a separate request. |
| `reconcile(peer, scope, budget, cursor)` | Schedule bounded repair, fetch and evidence work; expose incomplete scans and missing dependencies. |
| `request_history(source, scope, grant)` | Start an explicit import; report coverage/gaps and preserve provenance. |
| `progress(handle)` / `changes(cursor)` | Query durable facts. Notifications may be missed; they are not the sole record of completion. |
| `propose_change(change)` | Submit to the owner; return pending/effective/rejected/conflicted, never infer effectiveness from submission. |

Adapters supply authenticated transport, streaming, clock/entropy, transactional
storage, crypto provider and bounded scheduling. Application callbacks validate
schema, snapshot meaning and history permissions; application effects occur after
record acceptance with their own idempotency rules. No chat timeline or LXMF
schema belongs in the engine. PRNS already provides useful precedents for
[borrowed networking](../../../applications/services/lxmf/src/direct.rs) and
[caller-owned definitive commits](../../../applications/services/lxmf/src/mailbox.rs).

Retain the [shared outcome vocabulary](policies.md#discovery-and-protocol-outcomes),
adding `IdempotencyConflict`, `RestartInventory`, `TimeUncertain`,
`RecoveryRequired`, `HistoryUnavailable` and `EvidencePruned`. Bind responses to requests and
verified state; timeout remains unknown. Cap repair attempts per exchange, back
off on repeated identical corrections, and never answer errors with more errors.

## 9. Work that makes this implementable

The [embedded guide](embedded.md#release-gates) owns the current integration and
resource gates. Protocol completion also requires canonical wire/credential
vectors, delayed-epoch policy and barrier tests, private control bootstrap after
state loss, authorized history transfer, and independent interoperability.
Wire qualification includes invalid, fork and replay vectors, explicit rejection
of unsupported versions/profiles, and documented refusal at each published bound.

Exercise partitions, rejoin, remove/re-add, revoke/restore, duplicates, lost
replies, bounded storage and clock uncertainty. Preserve immutable IDs, targets,
deadlines and retry obligations. Chat and telemetry must use the same mechanism;
opaque custody remains a separately admitted role. Trial group sizes and payload
ceilings are workloads, not advertised supported limits.

The strict extension needs one further state machine: membership transitions and
admissions in the same durable order, admission evidence bound to the record,
audience and envelope, and no content release before approval. A removal ordered
first rejects a new stale attempt; a prior valid admission remains historical.
This requires an available, consistently fenced authority. A recent-head query
cannot substitute for it.

## 10. Evidence and known gaps

The [architecture source audit](design.md#security-and-sources-analyzed)
covers Reticulum Python, PRNS, RFed, Sesame and MLS. RFed's opaque storage and
inventory/fetch are useful patterns; its delivery queues do not supply the
transactional obligations above. Sesame informs independent endpoint repair;
MLS is the preferred private protocol, not a storage or application protocol.
The MLS source audit (separate integration) and
adapter limits (separate integration)
separate protocol requirements from the pinned backend's current behavior.

The remaining blockers are concrete: external wire/credential interoperability, private control bootstrap after state loss, permissioned
history transfer, qualification of the proposed key-update/deletion and
inactive-member policies, metadata exposure tests, numeric bounds/clock
qualification and measured bandwidth, including repair caused by routine rekeys.
Threshold governance, authority recovery, archive guarantees and production
security remain unqualified. Host recovery and transport tests exercise the
implemented slices; they do not establish all policies in this contract.
