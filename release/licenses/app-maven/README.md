# PRNS Chat Android dependency review

The app release review covers the external AARs and JARs selected for PRNS Chat by Gradle's `releaseRuntimeClasspath`. The reviewed profile contains 190 Maven coordinates and 178 external artifact files. Twelve coordinates contribute metadata for dependency resolution. The separate debug profile supplies two additional file variants. Build tools, local app and SDK projects, Android platform APIs and the separately installed Google Play services application have their own sources and delivery paths.

## Reviewed inputs

- `resolved-runtime.json` records coordinates, filenames, SHA-256 hashes and project components for both actual Gradle configurations. The Android qualification compares new resolution results with both profiles. A release build can shrink, merge and strip their contents.
- `pom-license-evidence.json` and `pom-sources/` preserve the 190 selected declarations and the parent documents they inherit from. `pom-origins.json` records each repository verification or Expo registry archive.
- `artifact-origins.json` records a byte match for every external file. The binaries came from Google Maven, Maven Central or the member of an integrity-verified npm archive identified by the Expo POM. Maven Central redirects two React Android artifacts to the React Native CDN. Five published Gradle module descriptors record different local and remote filenames for the same bytes.
- `artifact-notices.json` records AAR/JAR notices and nested `classes.jar` notices against their artifact hashes. Google's indexed notices use byte offsets into the companion text. `artifact-notice-sources/` preserves the original bytes. A source with gzip encoding has checksums for both forms.
- `release-review.json` binds the release coordinates, POMs, inherited declarations, filenames, hashes and origins. It records each coordinate's decision and supplementary copyright material, including packaged-source notices and native-library attributions. The inventory includes the upstream notices for React Native, libc++, Hermes, Fresco's image codecs, CameraX/libyuv, zstd and JNA/libffi. Reviewers can trace each text to its tagged source, source archive or npm member and SHA-256.

## App-specific decisions

PRNS selects Apache-2.0 for JNA 5.18.1. The artifact itself expressly offers Apache-2.0 or LGPL-2.1-or-later. The native libffi notice accompanies this selection. CameraX camera-core declares both Apache-2.0 and BSD-3-Clause for its embedded image-processing code.

Google's ML Kit documentation describes integrating the barcode model directly into an Android app. The qualified app includes the model files and native barcode library. The ML Kit and Google API terms govern this use. Image processing is local and the service can send performance and usage metrics. The Android app must provide the applicable end-user disclosure and open-source notices. Four selected client AARs declare the Android Software Development Kit License. Google documents integrating Play services client libraries into apps. Sections 3.1–3.5 of the declared SDK license cover compatible Android application development and restrict redistribution of the SDK. The project approved these four exact artifacts for the contact-card scanner in PRNS Chat on compatible Android devices, with offline notices in About and the scanner disclosure. The release input digest binds this decision to the reviewed binaries. Changed artifacts and other products need their own review. The record concerns the project's release policy. ## Product notices and verification

Run `python3 validation/security/app_maven.py --write-notices` to regenerate the Android app asset at `applications/prns/app/assets/licenses/android-maven.txt`. The text includes the selected release libraries, terms links and deduplicated copyright and license notices. The Android notices screen references this asset. Run `--check-notices` to compare the checked-in asset with the reviewed inputs. Run `--verify-apk PATH` on the actual assembled release app. The check reads the asset or raw Android resource and verifies its bytes after Metro and Android resource packaging have assigned the final name. The output identifies the APK member and its SHA-256.

New or changed dependencies require fresh Gradle resolution, binary origin verification, upstream notice review and product notice generation. Keep the Maven coordinates in an Apache, MIT or BSD group tied to their exact release POM declarations. Product receipt and app signing use the built application separately.
